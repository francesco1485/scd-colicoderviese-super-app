## Hard continuity rule

SCD ONE is the public/social/transactional evolution of the earlier SCD Universe work.

Before creating anything:
- search existing code;
- search previous contracts/tests;
- search R38-R56 implementation;
- classify KEEP / ENHANCE / FIX / INTEGRATE / COMPLETE / REMOVE_WITH_REASON;
- use REBUILD_IMPROVE only for obsolete presentation.

Never restart from zero merely because a screen is visually old.

## Product mission

Build SCD ONE into a world-class, high-scale digital club application where supporters, families, athletes, teams, staff-public-context, territory and external users can:
- understand what is happening now;
- follow sport and Matchday;
- live the SCD Week;
- discover teams and content;
- participate in safe community/social experiences;
- register for events/open days/tournaments;
- request services/fields where enabled;
- access tickets/cards/services;
- manage their authorized personal/family/athlete context;
- discover verified partner value;
- receive relevant notifications;
- complete real transactions with clear status and audit.

## Boundaries

Do NOT recreate:
- SCD CORE internal management;
- SCD GROW deep CRM/commercial workflows;
- Command R22 orchestration;
- R20 identity engine;
- duplicate database/calendar/source-of-truth.

Integrate them through contracts/adapters.

## Experience doctrine

Mobile first, not mobile only.

Canonical mobile bottom navigation:
HOME / CALENDAR / TEAMS / SOCIAL / PROFILE.

SCD Week:
FRIDAY -> FRIDAY, weekend-dominant.

Public home:
PULSE -> NEXT MATCH -> SCD WEEK -> TEAMS -> MATCHDAY -> NEWSROOM -> SOCIAL/MEDIA -> EVENTS -> PARTNER RAIL -> COMMUNITY/SERVICES -> JOIN/PROFILE.

The first viewport must always answer a useful current-state question.

## Visual doctrine

Use the canonical SCD palette and `SPATIAL_SPORT_EDITORIAL_HIGH_IMPACT`.

Reject obsolete portals, SaaS templates, Bootstrap-admin look, WordPress-theme look, card walls, brochure hero, framed-phone desktop, fake live widgets and casino/gambling aesthetics.

Use gaming energy only as clarity, progression, state and delight.

Use purposeful motion, synthetic/original spatial scenes and verified official assets.

## Data doctrine

No invented sport/business data.

Every user-visible fact should have:
- source;
- timestamp/freshness where meaningful;
- trust/authority;
- fallback state.

Use explicit unavailable/stale states.

Preserve one EVENT_ID and one PERSON identity.

## Social doctrine

Build SCD-specific community, not a generic social clone.

Safety:
- no unsafe adult-minor 1:1;
- no public minor ranking/profiling;
- consent-aware media;
- reporting/moderation;
- role-aware visibility.

## Transaction doctrine

Every transaction requires:
- unique ID;
- idempotency;
- validation;
- status machine;
- audit/provenance;
- confirmation;
- failure/retry;
- human approval where required.

A button without a completed backend workflow is NOT a finished feature.

## Scale doctrine

Design for high traffic:
- cache public reads;
- optimize assets/media;
- lazy-load where justified;
- resilient upstreams;
- rate-limit writes;
- idempotent mutations;
- use queue/orchestration for slow work;
- privacy-first telemetry;
- PWA/offline states.

Do not sacrifice correctness for apparent speed.

## Definition of professional completion

A vertical slice is complete only when:
- actual UI exists;
- actual backend/API path exists where needed;
- actual data contract exists;
- permissions are correct;
- missing/failure states exist;
- responsive states exist;
- accessibility exists;
- performance impact is understood;
- tests pass;
- source/provenance is preserved;
- no duplicate system was created;
- PR has evidence;
- handoff identifies the next safe block.

Do not stop at mockup, documentation or architecture when implementation is safely possible.
Do not claim production verification unless production evidence exists.
